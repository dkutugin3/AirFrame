### Этап 2 — ёмкость и временная шкала playout
- Изменено: резерв кадров `ceil(max_delay*fps)+3` (120 fps stable = 45 вместо 24); байтовый

  молчаливого уменьшения; пересоздание бюджета/шкалы при смене профиля/разрешения; метрики
  `playoutMaxFrames/BudgetMiB/ReservedMiB/Incompatible/SuggestionFps`.
- RED: 14 падений/10 ошибок, в т.ч. `AssertionError: 24 != 14` и `24 != 45`, отсутствие
  `incompatible`/`MAX_QUEUE_BYTES`/метрик.
- GREEN: `test_playout` 17/17. Измерено: реальный decoded 2560×1440 = 5 529 600 Б; резерв
  120 fps/2560×1440 = 237.3 МиБ (поддержан); 4:3 1920×2560@120 = 316.4 МиБ (отказ + 60 FPS).
- Не проверено: UI-отображение отказа (desktop — этап 1/5, метрики прокинуты).

### Этап 3 — ограниченное ожидание потерянных RTP-пакетов
- Изменено (`airframe/transport.py`, `receiver.py`): настраиваемый дедлайн 150 мс от
  **доказанного** разрыва sequence (пришёл более поздний пакет), независимый от ёмкости 2048 и
  playout; повторные пакеты не продлевают срок; по истечении повреждённая эпоха освобождается,
  поток ждёт полный IDR + SPS/PPS (VP8 — keyframe); PLI: первый сразу, повторы ≤1/500 мс, стоп
  после восстановления; таймер работает без новых пакетов; опоздавшие пакеты старой эпохи
  игнорируются; NACK немедленный, состояние сбрасывается при SSRC/reconnect; смена эпохи не
  сопровождается выдачей зависимых P-кадров.
- RED: старый baseline 2048 пакетов = **3.413 с** (`stage3-old-code-baseline.txt`); новые тесты
  падали `TypeError: ...unexpected keyword argument 'clock'`; receiver — нет PLI после потери.
- GREEN: `test_transport` 14/14, `test_receiver` 7/7, включая реальный WebRTC/H.264 тест с
  потерей пакета и RTX, PLI и возобновлением с нового ключевого кадра. Беспотерьная пауза 225 мс
  ложного PLI не даёт.

### Этап 4 — ограничение очередей до/после декодера
- Изменено: новый `airframe/decode.py` — узкий слой интеграции с aiortc 1.15.0: собственный
  decoder worker, ограниченная очередь закодированных кадров (количество/байты/возраст 150 мс от
  постановки access unit), ограниченная передача декодированных кадров (вмещает пачку
  225 мс/14 кадров, не latest-only), сброс эпохи + запрос IDR при переполнении (без drop-oldest
  зависимых кадров), фильтрация устаревших результатов, безопасное закрытие (повторное закрытие,
  старый worker не публикует в новый сеанс), метрики глубины/байтов/возраста/времени декода/
  восстановлений. Граница гарантии: уже выполняющийся нативный вызов FFmpeg не прерывается —
  закрытие ждёт только его; изоляция зависшего декодера — вне рамок (документировано).
- RED: `test_decode.py` 11 поведенческих контрактов + receiver-сценарии перегрузки/пачки.
- GREEN: `test_decode` 11/11, `test_receiver` 9/9, реальный H.264 после recovery декодируется.
- Отдельный follow-up `6ec6961`: no-op `BoundedDecodedQueue.put()` — aiortc при остановке своего
  decoder thread шлёт end-signal в старую очередь; убраны non-fatal traceback’и (RED:
  `AttributeError`, GREEN: 0 traceback в receiver-прогоне).

### Этап 6 — GPU/YUV-вывод
- Изменено: `airframe/render.py` — интерфейс рендерера, `QtVideoRenderer` (PyAV YUV → `QVideoFrame`
  → `QVideoSink`/`QVideoWidget`; на macOS рисует QRhi/Metal с shader `yuv_triplanar`) и
  `SoftwareVideoRenderer` (старый путь swscale→BGRA→QPainter), mailbox последнего готового кадра с
  pinning до конца использования; `desktop.py` переведён на YUV-путь, обязательный
  `frame.reformat("bgra")` убран из основного пути; скрытое окно не готовит кадры; оба окна
  делят один декодированный поток; «точный размер» OBS-окна = физические пиксели кадра (1:1,
  2560×1440 при logical 1280×720 @2x); видимые actual path/fallback reason.
- RED/контракты: цветовые таблицы BT.601/BT.709 limited/full с заранее зафиксированным допуском,
  stride/поворот/HiDPI/портрет/ландшафт, lifetime, fallback. Native: 24/24 цветовых патча в ±2
  кода ITU на Metal RHI; BT.601+full (до 26 кодов вне допуска) маршрутизируется в software и
  корректен в ±1; exact-size 1:1 подтверждён; CPU на кадр 1.511 vs 3.627 мс (YUV vs старый BGRA),
  2.07 мс/кадр в устойчивом окне.
- Не проверено: физический захват OBS (см. §4), Windows Qt RHI, GPU-время как отдельная метрика,
  zero-copy не заявлен (1 копия YUV/кадр).

### Этап 7 — аппаратный H.264-декод
- Изменено: `airframe/hwdecode.py` — PyAV 17.1.0 `HWAccel`/VideoToolbox; «контекст создан, но
  `is_hwaccel` False» = не успех; реальный IDR+P-поток декодируется аппаратно, кадры `nv12`,
  PTS/размеры/пиксели совпадают с software (0 кодовых отличий на 60 кадрах); отказ инициализации и
  отказ в середине сеанса → software с правильной точки IDR, видимая причина, без цикла повторов;
  `close()/reset()` освобождают контексты. В `receiver.py` — выбор фабрики и ключи
  `hwDecodeRequested/Mode/Verified/Reason`; не-H.264 кодеки делегируются штатному декодеру aiortc.
- **Измеренная польза:** аппаратный путь ~3.1 мс/кадр wall vs ~0.3 мс software (CPU 0.55 vs
  1.2 мс/кадр — только разгрузка CPU), PyAV скачивает кадры в RAM → **не zero-copy**. Поэтому
  `auto` оставляет проверенный более быстрый software; `hardware` — явный opt-in
  (`AIRFRAME_HW_DECODE=hardware`), проверенный в реальном receiver-сеансе (`hwDecodeVerified=True`,
  0 ошибок декода).
- Не проверено: Windows/D3D11VA; реальный Android SPS; отдельного выигрыша по задержке нет.

### Этап 8 — адаптивное качество (не реализовано)
План требует добавлять контроллер **после** измерений этапов 5–7 и фиксировать окончательные
пороги по отчётам целевого телефона. Реального телефона и измерительного прогона на нём в этом
окружении нет; фиксировать пороги «на глаз» запрещено планом. Этап честно оставлен как будущая
работа; в UI/README никаких обещаний адаптации нет.

### Этап 9 — H.264 High и HEVC
- High (desktop-часть, `7ee15c2` + ранее `010224e`/`f5a86c2`): scoped-расширение возможностей
  приёма H.264 High/Constrained High на время `setRemoteDescription` (варианты 64001f/640c1f),
  baseline fallback сохраняется; реальный libx264-High поток декодируется end-to-end; уровень в
  answer переписывается для требуемого профиля (`640c33`/`640033` при 2560@60). RED:
  `Failed to set remote video description send parameters` для High-offer; GREEN: полный Docker
  suite 167/167. Android High e2e не проверен (нет телефона), baseline остаётся профилем по
  умолчанию.
- Объявленный уровень: aiortc 1.15.0 всегда отвечает `42001f/42e01f` (level 3.1); добавлен
  `airframe/h264.py` (таблица уровней H.264, расчёт по MaxFS/MaxMBPS) и переписывание уровня в
  answer: 2560@60 → 42e033/5.1, 1920@60 → 4.2, 1920@30 → 4.0. RED 3/4, GREEN 4/4; локальный SPS
  реального 2560×1440@60 энкода = level_idc 51 (совпадает). Android-энкодер SPS не проверен.
- HEVC **не реализован и не заявлен**: в aiortc 1.15.0 нет H.265 в `CODECS`, `depayload` знает
  только VP8/H264, `get_decoder/get_encoder` не поддерживают `video/h265`; отсутствуют RFC 7798
  depacketizer, HEVC ftp/tier/level-согласование, HEVC-эпохи восстановления, проверка Android
  WebRTC factory/MediaCodec. Матрица недостающей работы:
  `artifacts/2026-10-30-stable60fps/core/stage9a-hevc-analysis.txt`.

## 4. Финальная приёмка (§13)

### A. Детерминированная и интеграционная — зелёная
- Финальный `sh scripts/verify.sh` на HEAD: **Docker 168 tests OK**, **native 74 tests OK**,
  логи `artifacts/2026-10-30-stable60fps/verify/20261030T030237Z/`.
- Причины первоначальных RED зафиксированы в отчётах рабочих потоков и в §3.
- Наблюдаемость: очереди/возраст/глубина, время декода, восстановления, пропуски по причинам,
  playout-бюджет/резерв, hwDecode-статус — в метриках; desktop-диагностика показывает
  capture/encoder/transport bottleneck, неизвестное ≠ 0.
- Ограничения памяти/времени: playout ≤256 МиБ (только очередь playout), RTP ≤2048 пакетов +
  дедлайн 150 мс, очереди декодера ограничены count/bytes/age, closed-safe.
- Версии и зависимости записаны (`artifacts/2026-10-30-stable60fps/VERSIONS.txt`,
  `packages/README-RELEASE.md`); smoke-скрипты переведены на новые UI-структуры и текущую папку
  артефактов.

### B. Выделенный компьютер, нативный поток и OBS — **не выполнено в этом прогоне**
Пользователь выбрал пропустить физический захват: активное пространство дисплея занято его
полноэкранным приложением, программно переключать Spaces нельзя (Accessibility запрещён), а
fail-closed harness отказался записывать неверное окно. Итог:
`artifacts/2026-10-30-stable60fps/acceptance/FINAL-STATUS.md`. Единственное реальное
внешне-захваченное доказательство — старый BGRA dry-run до этапа 6 (99.78 % уникальных ID,
p99 16.67 мс, 0 удержаний >50 мс, 0 underflow) — **не является** доказательством для нового
YUV/RHI-пути. Для нового пути есть только нативная проверка контракта/цвета/точного размера
(не физическая презентация) и in-process наблюдение активного Metal RHI. Точные команды для
повторного прогона на свободном дисплее — в `docs/ACCEPTANCE.md` и `FINAL-STATUS.md`.

### C. Качество — частично
Есть заранее зафиксированные допуски и BGRA dry-run сравнение (coding-loss floor 57.5 дБ/SSIM
0.9993; capture-path 27.5 дБ/SSIM 0.9252). Сравнение нового YUV/RHI-пути с BGRA в этом прогоне
не выполнено по той же причине отсутствия дисплея; нативная цветовая проверка (±2 кода ITU,
без перепутанных U/V, полный/ограниченный диапазон) — есть.

### D. Реальный телефон — **невозможно в этом окружении**
Устройство не подключено (`adb devices` пуст), установка Android SDK на хост запрещена планом.
Проверены только APK-сборка в Docker, JUnit/lint и статические контракты. Перезапуск, поворот,
блокировка, отзыв захвата, температура, реальный SPS/High — не проверены.

## 8. Ключевые решения (rulings)

1. Работа в отдельной ветке в основном дереве (без worktree) — Docker/venv/artifacts
   привязаны к каталогу; цена ошибки — обратимо через git.
2. Сохранение пользовательских правок отдельными `wip(user)`-коммитами до этапных коммитов.
3. Docker-приёмка через существующий образ с bind-mount (`scripts/test-docker.sh`) из-за
   sandbox-запрета записи в `~/.docker`; локальный `DOCKER_CONFIG` внутри рабочей папки.
4. `low`-режим playout хранит 1 кадр (нет временного резерва), формула резерва применяется к
   буферизующим режимам; 256 МиБ — только очередь playout.
5. `auto` для аппаратного декода выбирает проверенный software, т.к. измерения показали
   замедление; `hardware` — явный opt-in.
6. Физический захват §13.B/§13.C пропущен по решению пользователя (дисплей занят); результаты
   не выдумываются, старое BGRA-доказательство не подставляется под новый путь.
7. HEVC не заявлен; этап 8 не реализован без измерений на целевом устройстве.

### Review-проходка (I3, C1, I2, I6, I13) — реализована
Незакоммиченные RED-контракты из ревью доведены до GREEN:

- **I3 (профиль)**: Room разделён на `saved_profile` (желание, сохраняется сразу) и
  `effective_profile` (реально работает); переключение — только через применённый ack
  телефона с совпадающим requestId; при подключении телефона с нереализованным желанием
  запрос перевыдаётся (`requestId=""`). Session API отдаёт `effectiveSettings` /
  `savedSettings` / `pendingRequestId`; в desktop-процессе ack сверяется в
  `Receiver.send_json`. Сетевой контракт и поведение после таймаута/отклонения/стёртого
  ack покрыты `ProfileEffectiveSignalingTests` (7) и `EffectiveProfileReceiverTests` (3).
- **C1 (lost wake-up)**: `Frames.put` перевзводит уведомление, если диспетчер успел

  подготовленный кадр на каждый вывод (stride-скинутый предпросмотр не теряет кадр).
- **I6**: ошибки prepare считаются по каждому рендереру и видны в диагностике; панель OBS
  всегда активна (скрытое окно держит новейший кадр; открытие — мгновенно), отказ
  предпросмотра не останавливает записывающий вывод. Старый тест «скрытое окно OBS не
  готовит кадры» переписан под этот контракт ревью.
- **I13**: software-рендерер пинит исходный декодированный кадр на `PreparedFrame`;
  замена почтового ящика и конец сеанса не освобождают удержанный кадр.
- **I2**: точное окно OBS и диагностика считают поворот (выходной размер из последнего
