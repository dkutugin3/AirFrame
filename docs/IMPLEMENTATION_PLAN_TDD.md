## 1. Цель и границы

Реализуй максимально качественную передачу экрана Android по локальной сети с устойчивым выводом 60 FPS в отдельном настольном окне для OBS. DouWan — ориентир по пользовательскому результату, а не спецификация его закрытого протокола.

Сохрани:

- Собственное APK, MediaProjection и системное согласие на захват; без обязательных ADB, root и режима разработчика.
- Нативное настольное приложение Windows/macOS и отдельное чистое окно `AirFrame — OBS`.
- Прямую локальную передачу, QR/код, переподключение, управление профилем и громкостью.
- H.264 как совместимый базовый вариант; рабочий программный декодер как резервный путь.
- Раздельные режимы задержки. Буфер 250–350 мс — дополнительный запас воспроизведения, а не полная задержка телефон → OBS.

Базовый профиль нового сеанса: **60 FPS / 2560 px по длинной стороне / максимум 24 Мбит/с / стабильность OBS**. Профиль 60 FPS / 1920 px / 16 Мбит/с оставь для менее производительных условий. Битрейт — верхняя граница; не считай её фактическим видеобитрейтом.

120 FPS не является целью этой работы и не должен быть профилем по умолчанию. Существующий экспериментальный режим не должен ломать буфер или создавать ложные обещания: либо он проходит проверки ресурсов ниже, либо комбинация явно отклоняется с понятной причиной.

Не считай искусственное повторение одного изображения достижением 60 FPS. Статичный экран может захватываться реже; производительность оценивай на непрерывно движущейся сцене, которая действительно создаёт 60 новых кадров в секунду.

## 2. Правила TDD и порядок работы

Для каждого исправления соблюдай **RED → GREEN → REFACTOR**:

1. Напиши минимальный поведенческий тест, воспроизводящий дефект или новый контракт.
2. Запусти его на текущем коде и сохрани ожидаемую причину падения. Ошибка импорта, недоступный Docker или отсутствующее оборудование не являются RED.
3. Внеси минимальное изменение, чтобы тест прошёл.
4. Запусти связанные регрессии. Затем приведи код в порядок без изменения проверяемого поведения.
5. После завершения этапа прогони соответствующий набор целиком и зафиксируй результат.

Для нового GPU/аппаратного пути сначала зафиксируй контракт выбора, отказа, владения кадрами и резервного режима, а также сценарий реальной проверки. Моки проверяют поведение интеграции; ускорение и правильность настоящего декодирования доказываются отдельным нативным прогоном.

Не ослабляй пороги ради зелёного отчёта. Изменение порога требует объяснения и сохранения исходных результатов. Не добавляй тесты, которые лишь повторяют строки реализации. Уровни проверок:

- **Детерминированные:** виртуальные часы, настоящие данные и воспроизводимые входные последовательности. Без зависимости от точности системного таймера.
- **Интеграционные:** настоящий SDP/RTP/RTX/NACK/PLI и H.264-декодирование, настоящий Qt и жизненный цикл.
- **Производительность:** выделенный компьютер, реальный GPU, непрерывный прогон и запись OBS. Не подменяй этими замерами обычные CI-тесты и наоборот.

Headless-тесты оставляй в `tests/`. Тесты, которым действительно нужны Qt, окно, GPU или OBS, вынеси в отдельный набор, например `tests_native/`, с отдельной командой и окружением. Текущий Docker test-target не устанавливает PySide6: не добавляй в обычный discovery обязательные GUI-импорты и не скрывай непроверенный нативный путь за общим «все тесты прошли».

Android unit tests, lint и сборки APK выполняй через Docker. Основные Python-проверки и сборки также выполняй через существующий Docker-процесс. Проверки GPU, Qt и OBS запускай нативно на соответствующей ОС. Не устанавливай Android SDK на хост ради обхода Docker.

В кадре должен быть машиночитаемый номер, пригодный для проверки записи OBS. Проверяй соответствие извлечённого номера ожидаемому; простого наличия видимого таймера недостаточно.

Веди ограниченные интервальные метрики и, только в режиме диагностики, подробный поток событий в файл: сборка → начало/конец декодирования → готовность к выводу → отправка рендереру → завершение рендеринга, если API позволяет его наблюдать. `paintEvent` и передача кадра рендереру не являются доказательством физического показа или захвата OBS. Сопоставляй PTS/номера в синтетическом стенде. Не вычитай абсолютные часы телефона и ПК без их синхронизации.

Результат этапа: исходный отчёт и повторяемый стенд. Зафиксируй собственное ожидаемое поведение стенда тестами до его использования для оценки изменений.

## 6. Этап 3 — ограничить ожидание потерянных RTP-пакетов

Основные изменения: `airframe/transport.py`, интеграция с receiver, `tests/test_transport.py`, WebRTC-интеграционные тесты.

**RED:**

- Воспроизведи потерю sequence 1 при 10 пакетах на кадр и 60 FPS. На старом коде сборка ждёт примерно 3,41 с до переполнения.
- `test_retransmission_before_deadline_preserves_frame`: пакет восстановился вовремя — кадр собран целиком, PLI не отправлен.
- `test_unrecoverable_loss_expires_without_capacity_overflow`: оригинал и повторы потеряны; ожидание завершается по времени, а не после 2048 пакетов.
- `test_expiry_runs_when_no_new_packets_arrive`: после потери нет входящих пакетов; таймер восстановления всё равно срабатывает.
- Новые пакеты не продлевают срок уже обнаруженного разрыва; потеря первого PLI или ответного ключевого кадра не оставляет сеанс навсегда в ожидании.
- Полностью упорядоченный беспотерьный поток RTP приостановлен на 225 мс, затем приходит пачкой: нет ложного восстановления/PLI и все ID сохраняются. Это отдельный комбинированный тест transport → decoder → stable playout.
- Порядок пакетов, RTX, переход sequence 65535→0, большие IDR >128 пакетов, поздние пакеты прежней эпохи, поворот/перезапуск и ограничение частоты PLI.
- Реальный H.264: после пропуска повреждённой цепочки декодер возобновляет корректный вывод с нового ключевого кадра.

**GREEN:**

- Введи конфигурируемый срок ожидания неполного кадра с инъекцией монотонных часов. Начальный LAN-бюджет для тестирования: **150 мс от первого обнаруженного разрыва**, отдельный от ёмкости 2048 пакетов и от playout. Последующие пакеты этот срок не сдвигают.
- Разрыв означает доказанный пропуск sequence number, когда получен более поздний пакет. Не запускай этот срок просто от первого фрагмента кадра или от общей тишины RTP: aiortc может ждать следующего timestamp даже для уже полностью полученного кадра. Иначе срок 150 мс разрушит беспотерьную паузу 225 мс, которую должен сглаживать playout. Но если пропуск уже доказан, последующая тишина не отменяет его срок.
- Для каждого заблокированного неполного кадра учитывай возраст; при истечении срока освобождай повреждённую цепочку и переходи в ожидание ключевого кадра. Первый PLI отправляй сразу; при отсутствии пригодного ключевого кадра повторяй запрос по таймеру, начально не чаще одного PLI в 500 мс. Останавливай повторы после восстановления.
- Поддержи таймер без новых пакетов. Игнорируй опоздавшие пакеты уже сброшенной эпохи.
- Сохрани немедленный NACK из существующего механизма; периодические NACK-повторы, если нужны, добавляй отдельным изменением с ограничением срока жизни. После отказа от повреждённой эпохи не запрашивай её пакеты. Переподключение, новый offer и смена SSRC отменяют старые таймеры/NACK/PLI.
- Не удаляй произвольные H.264 P-кадры с последующей выдачей зависимых кадров как будто ничего не произошло. Для H.264 новая эпоха начинается с полного IDR и пригодных SPS/PPS; обычный intra-кадр не обязательно является точкой независимого перезапуска. Если VP8 остаётся согласуемым, реализуй и проверь соответствующее восстановление для VP8.

**Приёмка:** в виртуальном тесте восстановление инициируется не позже 150 мс + один шаг часов. При доставке тестового IDR через 20 мс после PLI поток возобновляется в пределах этого сценарного бюджета. Это не обещание реального сетевого восстановления за 170 мс. Большие ключевые кадры и нормальное переупорядочивание продолжают работать.

## 7. Этап 4 — ограничить очереди до и после декодера

Не ограничивай работу только текущим playout: исследуй очередь закодированных кадров aiortc и очередь декодированных кадров до `track.recv()`.

**RED:**

- Источник производит 60 FPS, искусственный декодер обрабатывает 30 FPS: глубина, возраст и память очередей не растут неограниченно.
- Краткая задержка декодера не разрушает исправную цепочку; длительная перегрузка запускает контролируемое восстановление с IDR и учитывается в метриках.
- Закрытие сеанса при заполненной очереди/незавершённой конвертации не зависает. Старый worker не публикует кадры в новый сеанс.
- Сигнал завершения worker не теряется из-за полной очереди; повторное закрытие безопасно. Завершившийся кадр прежней эпохи отсеивается до playout/Qt.
- Возврат нормальной скорости не вызывает многосекундное проигрывание устаревшего видео.
- Декодер выдаёт за один оборот event loop пачку из 14 корректных кадров, накопившихся за паузу 225 мс при 60 FPS: stable сохраняет все кадры для последующего равномерного вывода.

**GREEN:**

- Выдели узкий слой интеграции с aiortc: конструктор декодера, приём закодированного кадра, ограничение очередей, восстановление и очистка.
- Перед декодером ограничивай количество, байты и возраст; после декодера используй ограниченную передачу кадров. Начальный предел возраста ожидающих входных данных — 150 мс; числовые лимиты сделай согласованными с FPS и допустимым размером IDR.
- Возраст ожидания декодера считай от помещения готового access unit в локальную очередь. Не подставляй вместо него возраст исходного PTS или время сетевой задержки: иначе нормальная пачка после паузы будет ошибочно считаться перегрузкой декодера.
- Очередь декодированных кадров до playout должна вмещать поддерживаемую пачку, а не быть latest-only mailbox. Сохранение только последнего кадра уместно после планирования playout, у рендерера; раньше оно уничтожит данные, необходимые для сглаживания.
- Предел возраста относится к ожидающей работе, а не к уже выполняющемуся нативному вызову FFmpeg. Проверка эпохи должна отсечь запоздавший результат; не обещай прерывание зависшего decode обычной отменой asyncio. Изоляция зависающего нативного декодера потребует отдельного решения, если такой дефект действительно воспроизводится.
- Не блокируй сетевой event loop ожиданием освобождения очереди. При переполнении не делай обычный `drop oldest` для зависимых закодированных кадров: сбрось эпоху декодирования, запроси IDR и возобновись корректно.
- Не редактируй `.venv`, `site-packages` и готовые пакеты. Если публичных расширений aiortc недостаточно, оформи минимальный воспроизводимый патч/закреплённый fork с тестами совместимости и лицензией. Избегай глобальной подмены декодера для всех peer connection.
- Пока используются внутренние API, закрепи совместимые версии и явно проверяй их структуру при старте.

Добавь глубину/байты/возраст очередей, время декодирования, число восстановлений и пропусков по причине. Различай ожидание в очереди, декодирование и конвертацию.

**Приёмка:** при контролируемом конечном времени decode перегрузка оставляет очереди и задержку ограниченными, завершение сеанса корректно, H.264 после восстановления действительно декодируется. Отдельно укажи границу гарантии для уже выполняющегося нативного вызова.

**RED для FramePacer:**

- Нормальный вход 120 Гц с выходом 30/60; сохранённый режим 120.
- После timestamp около 5 секунд — сброс к 1 нс: первый кадр принимается, следующий через 1 нс отклоняется, кадр через целевой период принимается. Старый `next` не должен сохранять прежнюю шкалу.
- Смена 30→60→120→60, длинная пауза, нерегулярный вход, восстановление после сброса. Не требуй идеальных интервалов от нерегулярного источника и не генерируй фиктивные кадры.

**RED для измерений:** первый замер, новая сессия/обнуление счётчиков, одинаковое время, отсутствующие RTC-поля, NaN/Infinity, границы типов и ограниченная память. Старые сообщения telemetry остаются допустимыми, новые необязательные поля действительно доходят до UI и отчёта.

**GREEN:** исправь минимально pacer и введи:

- FPS и максимальный интервал захвата; FPS кадров, принятых pacer.
- `framesEncoded`, `framesSent`, фактический видеобитрейт из `bytesSent`.
- Среднее время кодирования из доступных накопительных RTC-счётчиков. Не называй его p95 отдельного кадра: агрегированных счётчиков для этого недостаточно.
- Фактические кодек/профиль, размеры, причина ограничения; имя реализации и аппаратный статус — только если их можно достоверно получить.
- Температурный статус Android, где поддерживается. Недоступное значение — `unknown`, а не ноль.

На этом этапе не меняй вслепую `MAINTAIN_RESOLUTION` на `MAINTAIN_FRAMERATE`: это способно скрыто уменьшить разрешение. Сначала собери измерения и сохрани текущую политику качества.

**Приёмка:** unit tests/lint/APK проходят в Docker; реальные показания различают «захват не дал 60», «кодировщик не успел», «передача/ПК не успели».

## 9. Этап 6 — GPU-вывод без обязательной конвертации каждого кадра в BGRA

Цель: передавать YUV/NV12 в GPU-рендерер, сохраняя нативное чистое окно и корректные цвета. Сначала проверь минимальный путь Qt Multimedia (`QVideoFrame` → `QVideoSink`/видеовывод) на закреплённой версии Qt. Выбор конкретного виджета сам по себе не доказывает GPU-ускорение. Если путь не подходит для внешних кадров/OBS, реализуй небольшой YUV-рендерер. Не переписывай всё приложение ради этого этапа.

**RED/контракт до реализации:**

- Известные кадры YUV420P и NV12 с нестандартным stride; портрет/альбом, поворот, resize и HiDPI.
- Цветовые таблицы с известной матрицей и full/limited range: нет перепутанных U/V, поднятого чёрного, обрезанного белого и изменения пропорций. Допуск сравнения с эталоном зафиксируй заранее для одинакового алгоритма масштабирования.
- Кадр остаётся валидным до завершения использования GPU; замена mailbox/закрытие/переключение сеанса не освобождают его раньше времени.
- Два окна используют один декодированный поток, уведомления не копятся, скрытый предпросмотр не создаёт ненужную работу.
- Программный резервный рендерер продолжает показывать видео при недоступности GPU-пути.

**GREEN:** вынеси рендерер за небольшой интерфейс, сохрани mailbox последнего готового кадра и отдельное планирование playout. В основном режиме убери обязательный `frame.reformat(format="bgra")`; обработай цветовые метаданные. Добавь отображение фактического пути вывода и причину fallback. Обнови состав зависимостей и упаковку, если нужны модули сверх PySide6-Essentials.

Добавь режим точного размера области вывода/описание её физических пикселей: максимальное исходное качество не должно незаметно превращаться в уменьшенное окно и повторное увеличение в OBS.

**Приёмка:** настоящий нативный тест и запись окна OBS показывают правильные ID, цвета, размер и устойчивость. Offscreen-тест проверяет контракт, но не подтверждает ускорение или пригодность источника OBS. Сравни CPU, GPU и интервалы с прежним путём на одинаковом потоке.

## 10. Этап 7 — аппаратное H.264-декодирование с явным резервным режимом

Начальный путь: PyAV `HWAccel` и `CodecContext.create(..., hwaccel=...)`, если это поддержано закреплённой совместимой версией; macOS — VideoToolbox, Windows — D3D11VA. Не обновляй PyAV/aiortc/Qt до последней версии без проверки совместимости, Python и упаковки.

Проверь и закрепи диапазон зависимостей aiortc перед выбором PyAV; исходная установка использует PyAV 17.1.0. Документация актуального master может описывать другую версию.

До приёмки аппаратного пути проверь корректность уже используемого согласования H.264 profile/level и фактического SPS для 2560/60. Исходный aiortc объявляет `42001f/42e01f`; флаг асимметрии уровней не заменяет проверку совместимости сторон. Не откладывай исправление неверного объявленного уровня до внедрения High/HEVC: это часть работоспособности базового профиля.

**RED/контракт:**

- Выбор `auto / hardware / software` для поддержанного и неподдержанного устройства.
- Контекст успешно создан, но фактическое аппаратное ускорение не включилось: это не успех.
- Настоящий IDR и последовательность зависимых кадров декодируются в аппаратном режиме; номера/PTS, размеры и цвет сопоставимы с программным эталоном.
- Отказ при инициализации и отказ во время сеанса: программный путь включается с корректной точки/IDR, причина видна, бесконечных повторных попыток нет.
- Смена разрешения, поворот, переподключение и закрытие освобождают ресурсы.

**GREEN:** подключи аппаратный декодер через слой этапа 4. `auto` выбирает подтверждённый рабочий путь, при отказе сохраняет работоспособность и сообщает фактический режим. Принудительный `hardware` должен честно сообщать невозможность аппаратного режима, а не подписывать программный как аппаратный.

Учти: PyAV может скачивать декодированный кадр в RAM. Поэтому аппаратный decode и zero-copy — разные свойства. Не заявляй zero-copy без проверки пути кадра. Сначала измерь пользу аппаратного decode + YUV-вывода; добавляй обмен GPU-поверхностями только если он необходим по результатам профилирования.

**Приёмка:** реальные прогоны на macOS и Windows отдельно. Подтверждены декодирование настоящего потока, фактический аппаратный режим и отсутствие ухудшения кадров/восстановления. Моки и список доступных устройств не закрывают приёмку.

## 11. Этап 8 — управление компромиссом качества и частоты

Добавляй после измерений этапов 5–7, отдельным изменением.

Два явных приоритета:

- **Качество:** сохраняет выбранное разрешение и честно сообщает, если устойчивые 60 FPS недостижимы.
- **Плавность 60 FPS:** разрешает управляемое снижение длинной стороны 2560→1920, если пользователь выбрал такой нижний предел. Ниже предела качество не снижается молча.

**RED:** одиночный плохой замер не меняет профиль; устойчивое ограничение разрешает один переход; ниже предела переход запрещён; возврат качества требует устойчивого восстановления; ручной профиль не перезаписывается автоматически; при нижнем пределе отображается «60 FPS не удерживаются». Проверь влияние фактического масштабирования внутри WebRTC, а не только отправленные параметры.

**GREEN:** реализуй небольшой контроллер с гистерезисом и конфигурируемыми окнами. Исходные значения для проверки: 3 последовательных секундных интервала ограничения до снижения, не менее 10 секунд между изменениями, 15 секунд устойчивого восстановления до повышения. Окончательные пороги выбери по отчётам целевого телефона и зафиксируй до сравнительного финального прогона.

Не форсируй 80 Мбит/с, постоянный битрейт или отключение контроля перегрузки как универсальное средство. Фактическое разрешение и частота должны быть видны пользователю.

## 12. Этап 9 — H.264 High, затем HEVC как отдельные согласованные возможности

Этот этап идёт после исправления стабильности и рабочего декодера/рендерера. Его нельзя заменить включением флага Android factory.

Сначала зафиксируй реально согласованный H.264 profile/level и ограничения аппаратного Android-кодировщика. Текущий флаг поддержки High на телефоне не доказывает согласование High с desktop.

**RED для High:** оба конца поддерживают профиль — выбирается совместимая пара profile/level и настоящий поток декодируется; один конец не поддерживает — остаётся H.264 Baseline/Constrained Baseline; смена профиля и потери не ломают восстановление. Проверяй фактический битовый поток, а не только текст SDP.

**RED для HEVC:** пересечение возможностей сторон, отсутствие поддержки на одном конце, реальные SDP и RTP packetization/depacketization, большие ключевые кадры, VPS/SPS/PPS, потери/RTX/PLI, новый IDR, поворот и H.264 fallback. Не объявляй HEVC, если хоть один обязательный участок тракта отсутствует.

**GREEN:** добавь codec capabilities и согласование только подтверждённых путей. Проверка конкретной Android WebRTC-сборки обязательна: наличие системного MediaCodec HEVC не означает наличия HEVC в WebRTC factory и RTP-стеке. Если нужен native-патч/сборка WebRTC, оформи отдельный закреплённый Docker-build и воспроизводимые исходники/лицензии. Не меняй весь транспорт автоматически ради кодека.

**Приёмка:** на целевом телефоне реально передаётся и декодируется выбранный кодек; H.264 fallback проверен. Сравни при одинаковых фактических разрешении, 60 FPS и видеобитрейте. Не выбирай HEVC по умолчанию, если на целевом устройстве он ухудшает устойчивость или не даёт подтверждённой пользы. Если сборка/устройство не позволяют реализовать HEVC, зафиксируй точную причину и недостающую работу; не объявляй этот этап выполненным.

## 13. Финальная приёмка

### A. Детерминированная и интеграционная

- Все прежние и новые функциональные тесты проходят; подтверждены причины первоначальных RED.
- В виртуальном stable-тесте при 60 FPS, достаточном запасе и паузах до 225 мс сохранены все ID без повторов, пропусков и опустошений.
- Невосстановленные пакеты, перегрузка декодера, смена профиля, поворот и переподключение имеют ограниченные память и время восстановления; действительный IDR возобновляет декодирование.
- Глубина/возраст каждой очереди наблюдаемы. Различаются источник, сеть, сборка, decode, подготовка и вывод.
- В каждой сборке сохранены версии и зависимости; smoke-скрипты работают с новой структурой UI и актуальной папкой артефактов.

### B. Выделенный компьютер, нативный поток и OBS

Задай эталонные CPU/GPU, ОС, частоту экрана, размеры окна, режим питания и настройки OBS. GUI-бенчмарки запускай по одному, без взаимного перекрытия окон. Источник и экран/OBS должны использовать согласованные 60 или 59.94 FPS. После прогрева 10 секунд выполни минимум 10 минут непрерывного движения.

Начальные целевые пороги, фиксируемые до финального прогона:

- В записи OBS присутствует не менее **99,5% ожидаемых уникальных кадров** движущегося источника за измерительный интервал; повторы и пропуски посчитаны отдельно.
- **p99 интервала между новыми кадрами не более двух периодов** источника; нет необъяснённых удержаний изображения дольше **50 мс** в контролируемом беспотерьном сценарии.
- Ноль опустошений stable при беспотерьном потоке без введённых пауз сверх бюджета.
- Нет роста очередей и задержки; память выходит на устойчивый уровень.

Это инженерные пороги приёмки на заданном стенде, не обещание математически идеальных 60 FPS на любой машине. При непрохождении найди причину; не называй 55 FPS успехом. Сохрани сырые события и отчёт с числителями/знаменателями, p50/p95/p99/max, пропусками, повторами, CPU/GPU, RSS, очередями, фактическими кодеком/декодером/разрешением/битрейтом.

### C. Качество

Сравни исходную версию и новую на одном lossless-источнике, при одинаковых **фактических** FPS, разрешении и видеобитрейте. Выравнивай кадры по ID; отдельно оцени кодирование и тракт декодирования/вывода. Сохрани одинаковые фрагменты мелкого текста, цвета, градиентов и движения.

PSNR/SSIM дополняй просмотром кадров и видео. Для замены декодера/рендерера не допускай новой потери деталей, неправильной матрицы/диапазона и скрытого масштабирования. Допуски цветового сравнения фиксируй до реализации с учётом округления. Для новых кодеков приложи сравнение качества и нагрузки; один усреднённый показатель не определяет победителя.

### D. Реальный телефон

На целевом Android, включая S26, если это устройство пользователя, выполни 30–60 минут непрерывного движения с записью OBS для выбранного рабочего профиля. Сравнивай версии при одинаковых сцене, разрешении экрана, ориентации, положении в сети и начальном температурном состоянии. По возможности компьютер подключён к роутеру по Ethernet. Не выдавай эту рекомендацию за доказательство виновности Wi-Fi.

Проверь начало/остановку, поворот, смену профиля, краткий разрыв сети, переподключение, блокировку и отзыв захвата. После отзыва разрешения не пытайся обходить повторное системное согласие. Полную задержку измеряй внешней съёмкой общего таймера/события; отдельно указывай добавленный playout-запас.

Если эталонная сцена телефона не создаёт ровно 60 новых кадров в секунду, сначала измерь частоту источника. Не приписывай отсутствующие исходные кадры приёмнику и не скрывай их повторами. Для точного подсчёта используй воспроизводимый тестовый контент с ID; для настоящей игровой сцены отдельно отчитай интервалы/замирания и ограничения источника.

Добавь команды для новых тестов и отчётов. Если Docker или целевое оборудование недоступны, заверши независимые изменения и проверки, но явно перечисли непроверенные платформы. Сборка Windows на macOS/Docker не заменяет запуск Windows-приложения. Программный fallback не доказывает работоспособность аппаратного пути.

В репозиторий должны попасть код, тесты, необходимые воспроизводимые патчи зависимостей, обновлённая документация и инструкции проверки. В отдельной папке артефактов — APK, пакеты приложений, контрольные суммы, версии, отчёты и материал сравнения. Не выдавай старые пакеты за сборки нового кода.

Для каждого этапа предоставь: что изменилось; какой поведенческий тест падал до изменения и почему; какие проверки прошли; где сырые результаты; что осталось непроверенным. Делай небольшие логически связанные коммиты, если рабочий процесс позволяет. Не добавляй вымышленные результаты оборудования.

Порядок поставки:

1. **Стабильность 60 FPS:** этапы 0–5 и соответствующая приёмка.
2. **Производительность ПК:** этапы 6–7 и настоящая проверка GPU/OBS.
3. **Максимальное качество:** этапы 8–9 и честное сравнение кодеков.

Не останавливай реализацию всего задания на первой поставке, если последующие этапы доступны. Но отмечай готовность каждого результата отдельно: «функционально проверено», «подтверждено на macOS», «подтверждено на Windows», «подтверждено на телефоне». Полная цель не считается достигнутой только на основании unit tests или синтетического localhost-потока.

## 15. Документация для проверки выбранных API

Перед изменением библиотечных API используй Context7: сначала resolve-library-id, затем query-docs по конкретной задаче. Проверяй API закреплённой версии, а не только актуального master.

- PyAV: https://github.com/PyAV-Org/PyAV/blob/master/docs/api/codec.rst и исходники закреплённой версии. В индексе `/pyav-org/pyav` есть аппаратный decode; старый сайт `/websites/pyav_stable` содержит устаревшее утверждение об отсутствии поддержки HW decoding.
- Qt: https://doc.qt.io/qtforpython-6/PySide6/QtMultimedia/QVideoFrame.html и документация выбранного видеовывода/версии.
- aiortc: https://github.com/aiortc/aiortc — проверяй исходники именно используемого тега, его codec capabilities, очереди и возможности расширения.
- Android WebRTC: https://github.com/webrtc-sdk/android — проверяй конкретный артефакт, аппаратные factory и доступный набор кодеков.
- DouWan: https://rd.douwan.video/gpu_en.html и https://douwan.video/release-en.html подтверждают аппаратное декодирование и HEVC, но не раскрывают его внутренний транспорт и алгоритм буферизации.
